### 점검 중 발견한 버그

- **(해결) 로컬 콘솔 [남은 N건 실행]이 결과가 있는 칸까지 다시 실행한다.**
  - `Home.tsx`가 `tcIds` 없이 시작하고, `run.ts`는 새 Run이면 `skipDone: false`를 넘긴다.
  - 그래서 자동 케이스 전체가 다시 실행되고, 실행할 때마다 `attempts`가 오른다.
  - 해결: 케이스를 고르지 않고 시작하면 결과가 있는 칸을 건너뛴다. 고른 칸은 결과가 있어도 다시 실행한다. 실기기(SM-S711N)로 확인했다.
- **(해결) `sink.progress` 주석이 실제 동작과 다르다.**
  - 주석은 "F-CY-06 칸 자동 선점"이라고 하지만 실제로는 Run 문서의 `currentTcId`를 갱신할 뿐 잠금이 아니다.
  - 두 실행자가 같은 대상 디바이스로 동시에 돌리면 같은 칸을 중복 실행한다.
  - 해결: 주석을 "진행 표시용이며 잠금이 아니다"로 고쳤다. 중복 실행 자체는 F-CY-06(칸 선점)이 해결한다.
- **(해결) `getCycle`이 사이클 스냅샷 해시를 쓰지 않고 현재 QA 문서의 케이스 내용을 붙인다.**
  - 사이클을 만든 뒤 재승인된 케이스가 아무 표시 없이 바뀐 내용으로 실행된다(F-CY-02).
  - 해결: 사이클을 만들 때 케이스 내용을 `cycles/{id}/cases`에 복사하고 `getCycle`은 그것을 읽는다. 보안 규칙이 사본과 `snapshot`·`docId` 수정을 막는다.
- **(해결, 갱신 때 추가) 트리 검증 포인트의 `state`·`count` 판정이 틀린다 (F-EX-03).**
  - `state`는 요소가 있기만 하면 일치로 봐서, 내부 상태("기록된다", "유지된다")를 확인하지 못해도 자동 Pass가 될 수 있었다. `count`는 항상 판단불가였다.
  - 해결: `state`는 기대 문장에 따옴표로 적힌 값이 있을 때만 비교하고 나머지는 판단불가다. `count`는 같은 id(없으면 같은 부모·클래스·크기)의 요소를 센다.
  - 실기기에서 선택된 인디케이터 dot은 트리에 노드가 없었다(5개 중 4개). 그래서 트리에서 기대보다 적게 세면 Fail이 아니라 판단불가로 둔다.
