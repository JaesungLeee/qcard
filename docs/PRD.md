## 1. 개요

### 1.1 한 줄 요약
기획서·스펙·User Flow·User Story 등 스펙 문서를 넣으면 AI Agent가 **앱 버전별 QA 문서(테스트 케이스)를 생성**하고, **실행자 PC에 연결된 Android 디바이스에서 직접 수행**하며, 실행자는 **로컬 콘솔에서 디바이스 화면과 Agent 판단을 실시간으로 지켜보고**, 팀은 **웹 대시보드에서 진행 상태와 결과를 공유**하는 QA 자동화 플랫폼.

### 1.2 배경 / 문제
- QA 시트 작성은 문서를 읽고 케이스를 손으로 풀어내는 반복 작업이라 시간이 많이 들고, 작성자에 따라 커버리지 편차가 크다.
- 스펙이 여러 문서에 흩어져 있어, 이번 버전에서 무엇을 테스트해야 하는지 한 곳에서 보기 어렵다.
- 기존 모바일 UI 자동화(Appium 등)는 스크립트 작성·유지보수 비용이 높고, 화면이 바뀌면 쉽게 깨진다.
- 자동화가 돌아가도 "지금 무엇을 하고 있는지", "왜 Pass인지"를 사람이 확인하기 어려워 결과를 신뢰하기 어렵다.
- 결과가 개인 PC·개인 시트에 흩어져 팀 단위로 공유·추적하기 어렵다.

### 1.3 해결 방향
1. 여러 스펙 문서를 **앱 버전당 하나의 QA 문서**로 통합 생성하고, 사람이 웹에서 검토·편집·승인한다.
2. 승인된 케이스를 Agent가 **스크립트 없이** 디바이스 화면을 보고 조작하며 수행한다.
3. 수행 과정은 **라이브 디바이스 화면 + 액션 오버레이 + 단계 타임라인 + Agent 판단 근거**로 실행자의 로컬 콘솔에 노출되고, 실행자는 언제든 개입할 수 있다.
4. 모든 판정에 **행동 의도 → 실제 화면 → 판정 이유**를 기록해, 사람이 필요할 때 웹에서 끝까지 따라갈 수 있게 한다.
5. QA 문서·사이클 진행 상태·실행 결과·증거는 **클라우드(Firebase)에 저장**되어 팀 전체가 같은 데이터를 본다. 라이브 화면은 공유하지 않고, 스텝별 스크린샷(P1부터 녹화 영상)을 증거로 공유한다.

## 2. 목표와 비목표

### 2.1 목표
- G1. 스펙 문서로부터 추적 가능한(Traceable) 앱 버전별 QA 문서를 자동 생성한다.

### 5.2 QA 문서 생성
앱 버전마다 스펙 묶음 전체에서 **QA 문서 1개**를 생성한다. QA 문서의 **기준(source of truth)은 Firestore의 케이스 문서**이며, 편집은 웹에서만 한다. MD는 버전별로 렌더링한 읽기 전용 산출물(다운로드·diff·보관용)이다. 생성 로직(프롬프트)은 스킬 형태로 관리한다. 생성은 웹에서 요청하고 **요청자의 호스트 에이전트가 수행**한다(요청자 본인의 Claude 플랜 사용, §8). 요청자의 호스트 에이전트가 꺼져 있으면 웹에서 켜라고 안내하고, 결과는 Firestore에 올려 팀 전체가 본다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |

| F-PF-01 | **준비 플로우**: "로그인 상태", "항목 2개 보유" 같은 공통 사전조건을 **QA 문서 버전마다** 정의(확인 조건 + 수행 스텝), 그 버전의 케이스가 이를 참조. 같은 ID·같은 내용이어도 버전마다 사본을 따로 두어, 앱이 바뀌어 새 버전에서 고친 플로우가 이전 버전 사이클에 영향을 주지 않는다. 스펙의 Given에서 준비 플로우 후보를 추출해 제안하고, 새 버전은 이전 버전의 플로우를 이어받는다(F-QD-08). | F-PF-08 | **계정 등록**: 웹 사이드바의 **테스트 계정** 화면에서 Admin·QA가 로그인 ID·비밀번호·TOTP 시드(선택, `otpauth://` URI 또는 base32)·메모·계정 종류를 등록·수정·삭제. 저장은 Functions를 거쳐 비밀값을 암호화하며(F-EX-09), **저장한 비밀값은 다시 보여 주지 않고** "설정됨·마지막 변경 시각·변경한 사람"만 표시, 바꿀 때는 새 값으로 덮어씀. **계정 종류는 필요할 때만 드러낸다** — QA 문서에 쓰인 종류가 "기본" 하나뿐이면 등록 폼에 종류 칸이 없고(모두 "기본"으로 저장) 화면은 계정 목록만 표시. "기본" 외의 종류가 쓰이면 등록 폼에 종류 선택(케이스에 쓰인 종류에서 고르거나 새로 입력)과 종류별 계정 수·케이스 수가 나타나고, 계정이 0개인 종류를 경고. Run 시작 전 로컬 콘솔이 선택한 케이스에 필요한 종류 중 배정할 계정이 없는 종류를 알림. 로그인 준비 플로우에서 **앱이 계정 정보를 거절하면**(비밀번호 오류·계정 잠김 메시지) 그 케이스 Blocked("로그인 실패"), 계정은 반납하되 "로그인 실패" 표시를 붙여 배정에서 제외(앱의 계정 잠금을 막기 위해) — 비밀번호를 고치거나 [표시 해제]하면 다시 배정. 요소를 못 찾는 등 계정 탓이 아닌 실패는 표시하지 않는다. 한 Run에서 같은 종류의 로그인이 2번 실패하면 플로우 탓으로 보고 그 종류의 계정을 더 배정받지 않는다(남은 케이스 Blocked "로그인 플로우 확인 필요") — 잘못된 플로우가 풀의 계정을 차례로 막지 않게. 리스 중인 계정은 삭제할 수 없음 | P0 |
| F-PF-09 | **원복 플로우·격리**: 계정 상태를 바꾸는 케이스(프리미엄 전환, 설정 변경 등)는 원복 플로우(준비 플로우의 한 종류, 확인 조건 + 수행 스텝)를 참조. QA 문서 생성 때 이런 케이스를 찾아 원복 플로우 후보를 제안. 케이스가 끝나면 판정과 상관없이 원복을 수행하고, 원복 결과는 그 케이스 판정에 영향을 주지 않음. **원복 실패, 또는 원복 플로우가 있는 케이스 도중 리스 만료**면 계정을 반납하지 않고 **격리**(배정 제외) — 웹 계정 목록에 사유·케이스·시각을 표시하고 Admin·QA가 직접 원복한 뒤 [격리 해제]. 되돌릴 수 없는 계정 변경(탈퇴·삭제)은 원복할 수 없으므로 Manual | P0 |
| F-PF-07 | **보조 디바이스(상대 사용자)**: 두 번째 디바이스·에뮬레이터를 상대 사용자로 두고 Agent가 함께 조작해 다중 사용자 케이스를 자동 수행 | P1 |

### 5.4 테스트 사이클
여러 실행자가 각자의 디바이스로 돌린 Run을 하나의 결과로 묶는 단위. 웹 QA 시트·요약·통과율은 사이클 단위로 계산한다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| F-CY-01 | 사이클 생성: QA 문서 버전 + 빌드 + **대상 디바이스 목록(모델 + OS 메이저 버전)** 지정. 실제 디바이스는 모델과 OS 메이저 버전이 같으면 같은 대상으로 보고, 정확한 OS 빌드·보안 패치는 결과에 기록 | P0 |
| F-CY-02 | **케이스 스냅샷**: 생성 시점의 승인된 케이스(TC ID + 내용 해시)와 그 내용을 사이클에 복사해 고정 — 이후 QA 문서가 바뀌어도 사이클은 고정된 내용으로 실행. 재승인된 케이스를 "새 버전 있음"으로 표시하고 QA 권한자가 선택적으로 반영(반영한 케이스의 결과는 N/T로 초기화)하는 것은 P1 | P0 |
| F-CY-03 | Run은 사이클에 소속. 대상 목록에 없는 디바이스로는 실행하지 않음(P1: 실행하면 결과 컬럼 추가) | P0 |
| F-CY-04 | 같은 케이스·같은 디바이스 재실행 시 **최신 결과가 최종**, 이전 시도는 이력으로 보존(리포트에 "재시도 N회" 표시) | P0 |
| F-CY-05 | 진행 매트릭스: 케이스 × 대상 디바이스의 완료/실행 중(실행자 표시)/남은 칸, 실시간 반영 | P0 |
| F-CY-06 | **칸 자동 선점**: 케이스를 시작하는 순간 해당 "케이스 × 대상 디바이스" 칸을 잠금(Firestore 트랜잭션). 같은 대상 디바이스로 실행 중인 다른 Run은 잠긴 칸과 완료된 칸을 건너뛰고 남은 칸을 가져감. 케이스 종료·Run 중단·호스트 연결 끊김(하트비트 만료) 시 잠금 해제. 리스는 테스트 계정 배정(F-PF-04)의 Run 연결 신호를 그대로 쓴다. **구현**: 잠금은 Run 문서의 지금 칸(`currentTcId`) — Functions(`claimCell`)가 같은 대상 디바이스의 Run들과 그 칸의 결과를 트랜잭션에서 읽고 정하며, 호스트는 지우기만 한다(보안 규칙). 칸을 잡은 Run = 실행 중이고 연결 신호가 90초(`RUN_STALE_MS`) 안. 일시정지된 Run은 진행 중 케이스 결과를 쓰지 않으므로 칸을 놓는다. 호스트는 앞 케이스 결과를 올린 뒤 다음 칸을 잡고(결과가 큐에 남은 채 칸을 옮기지 않게), 칸을 잡지 못할 만큼 네트워크가 끊기면 "네트워크 끊김"으로 일시정지. 연결 신호는 업로드 큐를 거치지 않고 바로 보내(밀린 업로드 때문에 살아 있는 Run의 칸을 뺏기지 않게), 케이스 도중 신호를 60초 넘게 남기지 못했으면(네트워크 끊김·PC 절전) 다른 Run이 가져갔을 수 있으므로 다음 턴에서 멈추고 결과를 버린 뒤 "호스트 연결 끊김"으로 일시정지(남이 가져간 칸에 플랜 사용량을 쓰지 않게). 건너뛴 칸은 결과를 쓰지 않고 로컬 콘솔 큐에서 뺀다. 다시 실행(F-CY-04·07)으로 고른 칸은 결과가 있어도 돌리되, 다른 Run이 잡았거나 이 Run이 시작한 뒤(이어서 실행이면 처음 시작한 시각) 다른 Run이 끝낸 칸은 건너뛴다. 웹에서 시작한 Run(F-CY-08)은 기본 실행과 같다. 공개 출시 조건(§10) | P0 |
| F-CY-07 | **실행 케이스 선택**: Run 시작 시 기본값은 "이 디바이스의 남은 칸 전체"(결과가 있는 칸은 건너뜀). 기능(스펙)·우선순위·현재 판정(Fail·Blocked·확인필요 재실행)·수행 방식 필터와 개별 체크로 일부만 선택. 완료된 칸을 명시적으로 고르면 재실행(F-CY-04) | P0 |
| F-CY-08 | **웹에서 Run 시작**: QA 시트 머리의 [내 호스트에서 실행]·[이어서 실행]이 작업(`run_cycle`)을 만들고, **요청자 본인의 호스트**가 받아 로컬 콘솔과 같은 경로로 시작. 호스트가 꺼져 있으면 켜는 방법을 안내하고, 폰 잠김·다른 Run 진행 중이면 작업을 실패로 남김. 케이스 고르기는 로컬 콘솔에서 | P0 |
| F-CY-09 | **사이클 완료**: QA 권한자가 사이클을 완료로 표시. 확인필요·N/T 칸이 남아 있으면 건수를 경고하고 확인받음. 완료된 사이클은 새 Run을 받지 않고(사람 확정은 계속 가능), 사이클 목록에서 "시작 전"·"진행 중"·"완료" 칩으로 나눠 완료 쪽으로 옮긴다(별도 보관함 없음, 개발 서버의 로컬 실행 사이클은 "로컬 실행" 칩에 따로 둔다, 완료 기록은 사이클 간 비교 F-RP-15·놓친 결함 F-RP-08의 기준이라 숨기지 않고 남긴다). 완료를 취소해 다시 열 수 있음 | P0 |
| F-CY-10 | **사이클 삭제**: 잘못 만든 사이클(빌드·QA 문서·대상 선택 실수)을 지운다. QA 권한자만, 사이클 이름을 입력해 확인하고 지워질 결과·Run·결함 건수를 보여 준다. 완료된 사이클은 먼저 다시 열어야 삭제할 수 있고(실수로 완료 기록을 지우지 않게), 실행 중인 Run이 있으면 거부. 유예 없이 즉시 영구 삭제하며, Functions가 사이클의 하위 문서(케이스 사본·결과·Run·시도·결함·판정 이력)와 Storage `projects/{p}/cycles/{c}/` 아래 증거를 지운다(클라이언트는 사이클 문서를 직접 지우지 못함). 빌드·QA 문서는 남는다 | P0 |

## 6. 시스템 아키텍처

### 6.1 배포 형태
**실행·관찰은 로컬, 결과는 클라우드 공유.** 라이브 화면은 실행자만 보면 되므로 영상은 실시간으로 PC 밖으로 나가지 않고, 팀 공유가 필요한 데이터(QA 문서·사이클 진행 상태·결과·증거·녹화)만 Firebase에 저장한다. 자체 서버를 운영하지 않는다.

- **Web Dashboard** — 브라우저로 접속(Firebase Hosting, `https://qcard.dev`). 스펙 업로드, QA 문서 편집·승인, 사이클·진행 상태, 결과·리포트. 별도 설치 없음.
- **Firebase (BaaS)** — Auth, Firestore, Storage, Cloud Functions. GCP 서울 리전(`asia-northeast3`).
- **Host Agent** — 디바이스가 꽂힌 실행자 PC(**macOS**)에서 실행. `localhost`로 **로컬 콘솔**을 띄우고, Firebase로는 아웃바운드 연결만 사용하므로 포트 개방이 필요 없음. **LLM 호출은 같은 PC에 설치된 Claude Code(사용자 본인 로그인)를 헤드리스로 실행해 처리**하며(§8), 사용자가 웹에서 요청한 QA 문서 생성·리포트 작성도 그 사용자의 호스트 에이전트가 수행한다.

**제약**: 실행자는 디바이스가 연결된 PC 앞에 있어야 한다. 공용 디바이스 PC를 원격으로 실행·관전하는 시나리오는 범위 밖이며(§2.2), 필요해지면 호스트 에이전트에 미디어 중계(SFU, 예: LiveKit Cloud)를 붙여 확장한다.

### 6.2 구성 요소

```

┌──────────────────────┴──────────── Firebase ───────────────────────────────┐

└──────────────────────▲─────────────────────────────────────────────────────┘

┌──────────────────────┴─── Host Agent (실행자 PC, macOS) ───────────────────┐

```

**Executor를 호스트 에이전트에 두는 이유**: 관찰→판단→액션 루프에서 디바이스와 가장 가까운 곳에서 돌아야 디바이스 제어 지연이 적고, 녹화·스크린샷 같은 대용량 데이터를 로컬에서 처리한 뒤 필요한 것만 업로드할 수 있다. 판단은 같은 PC의 Claude Code를 거쳐 Anthropic으로 가므로 네트워크가 끊기면 Run은 일시정지한다(F-EX-13).

**LLM 작업을 모두 호스트에 두는 이유**: LLM 비용을 각 사용자의 Claude 플랜으로 부담하려면, 호출이 그 사용자가 로그인한 Claude Code에서 나가야 한다(§8). 그래서 클라우드에는 LLM을 부르는 구성 요소를 두지 않는다. 웹의 QA 문서 생성·케이스 수정안 요청·Run 시작은 Firestore 작업 문서로 만들고, 요청자의 호스트 에이전트가 구독해 처리한다. 호스트는 처리할 수 있는 작업 종류를 연결 신호로 알리고, 웹은 이를 보고 업데이트가 필요한 이전 버전 호스트를 안내한다.

**화면을 로컬에서만 보는 이유**: 실행 관찰은 실행자 1명만 필요하므로, 영상을 서버로 중계하지 않으면 미디어 서버 운영·NAT 통과·대역폭 문제가 사라진다. 팀원은 진행 상태를 실시간으로, 화면은 녹화·스크린샷으로 사후 확인한다.

### 6.3 Agent 구조
| Agent | 실행 위치 | 역할 | 입력 → 출력 | 모델 |
| --- | --- | --- | --- | --- |
| **QA Doc Generator** | Host (요청자) | 스펙 TS·EC 행 → 실행 가능한 케이스 변환(신규·변경 케이스만), 스펙 확인 질문, 스펙 보강 제안, 답변 기반 케이스 수정안(F-QD-17). 매칭·동일 케이스 복사는 LLM 없이 코드로 처리 | 앱 버전 스펙 묶음 + 이전 QA 문서 → QA 문서(케이스 문서) / 케이스 + 출처 행 + 답변된 질문 → 수정안 | Opus 5.5 |
| **Executor** | Host | 화면 관찰 → 액션 결정 → 디바이스 조작 루프, 준비 플로우 수행 | 케이스 + 디바이스 → 스텝 타임라인 | Sonnet 5.5 |
| **Verifier** | Host | 검증 포인트 판정과 근거 작성(Executor와 분리해 자기확증 편향 완화). 트리 포인트는 대상 요소 탐색만 하고 값 비교는 코드, 비전 포인트는 화면으로 판정 | 화면/트리 + 기대결과 → 판정 | Sonnet 5.5 (고정) |
| **Reporter** (P1) | Host (요청자) | 결함 리포트 초안(F-RP-13). 사이클 요약(F-RP-01)은 LLM 없이 코드로 계산 | 실행 결과 → 리포트 | Sonnet 5.5 |

Haiku 5.5는 판정이 아닌 보조 작업(화면 변화 감지, 팝업 분류, 로딩 대기 판단 등)에만 사용한다.

**LLM 호출 방식**: 모든 Agent는 `LlmClient` 인터페이스 하나로 LLM을 부르고, 기본 구현은 사용자 PC의 Claude Code CLI를 헤드리스로 실행한다(`claude -p`). 모델은 `--model`, 추론 강도는 `--effort`, 구조화 출력은 `--json-schema`로 지정한다. Executor의 액션 선택도 구조화 출력으로 받아 기존 도구 호출 형식으로 바꾸므로 실행 루프는 LLM 제공 방식과 무관하다. Claude Code의 내장 도구(셸·파일 편집 등)는 모두 끄고, 사용자 설정·프로젝트 설정·세션 저장을 읽거나 남기지 않게 실행한다. 사용자의 플랜에서 쓸 수 없는 모델이면(예: Opus) 시작 전에 안내한다. 개발·테스트용으로 Anthropic API 키 구현과 녹화·재생 구현을 함께 둔다.

### 6.5 기술 스택 (채택)

**원칙**: 대시보드·클라우드 함수·호스트 에이전트를 **TypeScript 단일 언어 모노레포**로 구성한다. 디바이스 제어(ADB)는 언어와 무관하고 모바일 자동화 도구(Appium 등)도 Node.js 생태계에 있으며, 웹-함수-호스트 간 데이터 스키마를 하나의 타입 정의로 공유할 수 있어 세 컴포넌트가 계속 맞물려 변경되는 이 제품에 유리하다. 서버 인프라는 Firebase 관리형 서비스로 대체해 운영 부담을 없앤다.

| 영역 | 채택 | 근거 |
| --- | --- | --- |
| 모노레포 | pnpm workspace + Turborepo | `apps/web`, `apps/functions`, `apps/host-agent`, `packages/shared`(스키마·스펙 파서·QA 문서 MD 렌더러·UI 컴포넌트) |
| 공유 스키마 | Zod | Firestore 문서·QA 문서 케이스 블록·LLM 구조화 출력 검증을 한 곳에서 정의 |
| Web | React 18 + Vite + react-router + TanStack Query, 그리드: AG Grid, 디자인 시스템 Montage(`packages/ui`) | 대용량 케이스 그리드. 로컬 콘솔 화면도 같은 코드베이스(`apps/web`의 `console`)를 호스트에 내장해 재사용 |
| 백엔드 로직 | Cloud Functions(2nd gen, Node.js) — 초대·호스트 연결·호스트 토큰 발급·프로젝트 삭제·집계·Webhook. LLM을 부르는 작업은 두지 않음(§6.2) | 서버 운영 없음, TS 친화 |
| DB | Firestore | 실시간 구독(진행 상태 공유), 보안 규칙 |
| 작업 큐 | Firestore 작업 문서(Job) → 요청자의 호스트 에이전트가 구독·처리 | QA 문서 생성 등 LLM 작업을 요청자 본인의 Claude 플랜으로 처리 |
| 파일 저장 | Cloud Storage for Firebase | 스펙·빌드·스크린샷 / (P1) QA 문서 MD·영상 |
| 호스트 업로드 큐 | 로컬 디스크 큐 | 네트워크 끊김 시 결과·증거 보관 후 재전송 |
| 인증 | Firebase Auth — 웹은 GitHub 제공자 단일(로그인 페이지, 팝업). 호스트는 Functions가 호스트 자격을 확인하고 발급한 커스텀 토큰(호스트 클레임) | 대상 사용자(앱 개발 팀)는 GitHub 계정을 보유하고 결함 연동도 GitHub. 제공자 1개라 계정 충돌·초대 기준 분리가 없음. 로그인 장소를 웹 하나로 모으고, 호스트에 GitHub 토큰을 두지 않으며, 보안 규칙이 호스트 쓰기와 사람 쓰기를 구분 |
| 비밀값 | Secret Manager(GitHub App 개인 키) / Cloud KMS + Firestore(테스트 계정 비밀값) | 계정 비밀값은 수가 많고 프로젝트와 함께 지워야 하므로 KMS로 암호화해 Firestore에 두고 Functions만 복호화. LLM 자격 증명은 다루지 않음 — §8 |
| 결함 트래커 연동 (P1) | **GitHub App**(대상 리포지토리에 설치) + Webhook → Cloud Functions | 리포지토리 단위 최소 권한(Issues 읽기/쓰기), 이슈 상태 Webhook 수신. 이슈 작성자는 App 봇, 본문에 보고자(@GitHub 사용자명) 표기 |
| Android 제어 | ADB 직접 호출 — 접근성 트리는 `uiautomator dump`, 입력은 `input`, 한글은 ADBKeyboard(입력할 때만 IME 전환). `DeviceDriver` 인터페이스 뒤에 두고 테스트는 `FakeDevice` | 설치 부담 없음. Appium은 필요해지면 같은 인터페이스 뒤에 추가 |
| Android 화면 | scrcpy H.264 → 브라우저 WebCodecs 디코딩(Chrome 계열). 로컬 콘솔을 보는 동안에만 띄움. (P1) 녹화 겸용 | 저지연·고프레임, 서버 불필요 |
| LLM | **Claude Code CLI 헤드리스(`claude -p`), 사용자 본인 플랜** — §6.3 모델 배치. 개발·테스트용 Anthropic API 키 구현, 녹화·재생 구현 병행 | 사용자별 과금, 판정은 Sonnet 고정. Claude Code 설치·로그인·최소 버전은 Run·QA 문서 생성 시작 전에 점검(F-EX-17) |
| 배포 | Firebase(Hosting·Functions·규칙)는 GitHub Actions가 `main` 푸시 때 배포. 호스트 에이전트는 npm `@qcard/host`(명령 `qcard connect`·`qcard serve`), 태그 `host-v*`로 배포. 로그인 시 자동 시작·앱 링크는 두지 않고 실행자가 QA할 때 `qcard serve`로 켬(트레이 앱은 M3). Claude Code는 사용자가 직접 설치·로그인 | 설치 단순화, QA하지 않을 때 실행자 PC에서 돌지 않음 |

**호스트 OS**: 실행자 PC는 모두 macOS이므로 호스트 에이전트는 **macOS만 지원**한다. Windows/Linux 지원은 범위 밖.

## 8. 보안 및 데이터 처리

이 제품은 다음 데이터를 **Anthropic으로 전송**한다.
- 스펙 문서 원문과 이미지(미공개 기획서·와이어프레임)
- 실행 중 디바이스 스크린샷과 화면 구조(테스트 계정 정보, 개인정보성 데이터가 화면에 보일 수 있음)

**결정: 옵션 D — 사용자 본인의 Claude Code 경유** (v0.7 확정, v0.3의 옵션 A를 대체)

| 옵션 | 내용 | 상태 |
| --- | --- | --- |
| A. 외부 API 직접 사용 | Anthropic API 키 + 클라우드 LLM 프록시 | v0.3 채택 → **v0.7 제품 경로에서 제외**. 비용을 운영자가 부담하거나 공용 키가 필요해 "사용자별 본인 플랜 부담" 요구와 맞지 않음. API 키 구현은 개발·테스트용으로만 유지 |

| C. 외부 전송 불가 | 사내 호스팅 모델 사용 | 미채택 |
| **D. 사용자 본인의 Claude Code** | 각 사용자 PC에 설치·로그인된 Claude Code CLI를 호스트 에이전트가 헤드리스(`claude -p`)로 실행 | **채택** — 사용자별로 본인의 Claude 구독 플랜(Pro·Max 등)에서 차감 |

옵션 D의 근거와 경계:
- Anthropic은 Free·Pro·Max 플랜의 OAuth 인증을 **Claude Code와 Claude.ai 전용**으로 두고, 그 토큰을 Agent SDK를 포함한 다른 제품에서 쓰거나 제3자가 사용자 대신 구독 자격 증명으로 요청을 보내는 것을 허용하지 않는다(2026-02 문서 갱신). 그래서 qcard는 **Agent SDK·OAuth 토큰을 쓰지 않고**, 사용자가 직접 설치·로그인한 Claude Code를 헤드리스 모드(스크립트·자동화용 공식 기능)로 실행한다.
- qcard는 Claude 자격 증명을 **읽거나 저장·전달하지 않는다**. 요청은 그 사용자의 PC에서, 그 사용자의 실행·생성 요청에 대해서만 나간다. 다른 사용자의 요청을 대신 처리하거나 계정을 공유하는 경로는 두지 않는다(계정 공유·재판매는 Anthropic 정책 위반).
- 2026-10-24 조사로 **조건부 허용**으로 판단했다(근거·지킬 조건은 §13 남은 질문 5). 남은 일은 Commercial Terms 동의와 Anthropic 서면 확인이며, **서비스를 외부에 공개하기 전에** 끝낸다(§10 공개 출시 조건).

운영 방식:
- 호스트 에이전트는 Claude Code를 실행할 때 내장 도구(셸·파일 편집·웹 등)를 모두 끄고, MCP 서버를 불러오지 않으며, 사용자·프로젝트 설정을 읽지 않고, 세션을 디스크에 남기지 않는다. 시스템 프롬프트는 qcard 것으로 대체한다. 모델이 할 수 있는 일은 qcard가 정한 출력 형식으로 답하는 것뿐이다.
- 대상 앱이 포그라운드가 아니면 스크린샷을 보내지 않는 규칙 등 전송 제한은 호스트 코드에서 강제한다(F-EX-02). **사람 전용 구간**(본인인증·인증번호 등, F-EX-10)에서는 화면 구조·스크린샷을 LLM에 보내지 않는다. 그 구간의 증거 스크린샷은 찍어 Storage에 올리므로, 실행자가 입력한 개인정보가 프로젝트 멤버에게 보일 수 있다 — 본인인증 우회가 있는 QA 빌드를 권장한다.
- 개인 플랜에는 ZDR(데이터 미보존)이 없다. 전송된 데이터는 **실행한 사용자 Claude 계정의 데이터 정책**(학습 사용 허용 설정에 따라 보관 기간이 다름)을 따른다. 프로젝트 생성·참여 시 이를 안내하고 확인받으며(F-TM-13), 실데이터 투입 여부는 프로젝트 Admin이 판단한다. 학습 사용을 끄도록 안내한다.
- **지원하는 로그인은 Claude 구독 플랜뿐이다.** Console 계정·API 키·Bedrock·Vertex로 로그인한 Claude Code(API 크레딧 과금)는 지원 대상이 아니며, 상태 표시·사전 점검·한도 처리(F-EX-17, F-DB-09)에서 따로 다루지 않는다. 플랜 이름은 Claude Code가 알려 주는 값을 그대로 보여 주고 특정 플랜의 한도 구조(5시간·주간 등)를 가정하지 않는다.
- 개발·테스트(이 저장소의 `pnpm verify`, 녹화)는 녹화·재생 또는 API 키 구현으로 하며, 더미 앱·합성 화면을 쓴다.

공통 요구사항:
- **테스트 계정 비밀값**: qcard 서버가 보관한다. Cloud KMS로 암호화해 클라이언트가 읽을 수 없는 Firestore 컬렉션에 두고, 웹에서 쓴 값은 다시 보여 주지 않는다. 계정을 리스한 실행 중 Run의 실행자 호스트만 배정 응답으로 받아 메모리에만 두며, 꺼낼 때마다 감사 로그를 남긴다(F-EX-09). 같은 프로젝트의 QA 역할은 실행을 통해 평문을 얻을 수 있다 — 테스트 계정은 팀이 공유하는 값이라는 전제다. 서버가 외부 팀의 계정 비밀번호를 보관하므로 개인정보처리방침에 적고, **실제 서비스 계정 대신 테스트 전용 계정을 쓰도록** 등록 화면에서 안내한다
- LLM 프롬프트에는 비밀값 대신 플레이스홀더, 로그·리포트·화면 구조에서 마스킹. 비밀번호 칸은 화면에 가려져 보이므로 스크린샷은 따로 가리지 않음
- 스크린샷 내 지정 영역/요소 마스킹 규칙(예: 주민번호 입력란) 설정 가능 (P1)
- LLM으로 전송한 데이터 감사 로그
- 라이브 화면은 실시간으로 실행자 PC 밖으로 전송하지 않음. 클라우드에는 증거용 스크린샷·녹화만 저장(GCP 서울 리전)
- 수동 결과에 사람이 첨부한 스크린샷(F-RP-05)은 웹에서 Storage로 바로 올라가고 LLM에는 보내지 않는다. 프로젝트 멤버 모두가 보므로 본인인증 화면처럼 개인정보가 보이는 화면은 올리지 않는다 — 첨부를 필수로 두지 않은 이유 중 하나
- **호스트 자격**: 비밀값은 실행자 PC의 macOS 키체인에만 두고 서버에는 해시만 저장. 호스트 토큰은 짧은 수명이며, 보안 규칙이 호스트 쓰기마다 연결 상태를 확인해 해제된 PC의 쓰기를 즉시 막음(F-TM-14)
- Agent 기록(Run, Agent 판정 결과, 이전 시도, 스크린샷)은 그 Run을 실행한 사용자의 호스트(호스트 토큰)만 쓸 수 있음. Run에 실행자 uid를 남기고 보안 규칙이 확인하며, 같은 사용자가 다시 연결한 PC는 이어서 쓸 수 있음. Run 상태(실행 중)는 보지 않음 — 업로드 큐로 늦게 도착한 결과를 받아야 하므로(F-EX-13). 사람은 결과 칸에서 판정·메모와 첨부 스크린샷(F-RP-05, 판정 확정과 함께만)만 바꾸고 Agent 증거(단계·검증 포인트·Run)는 못 바꿈. 그래도 실행자가 자기 호스트를 통해 Agent 결과를 조작할 여지는 있음 — 프로젝트 멤버 간 신뢰를 전제로 감수하고(다른 프로젝트에는 영향 없음), 사람 판정만 보안 규칙(판정자 = 로그인 사용자, 서버 시각)과 변경 불가 이력으로 강제(F-RP-04)
- 모든 통신 TLS, Firestore·Storage 접근은 보안 규칙으로 프로젝트 멤버·역할에 따라 제한. 여러 팀이 쓰므로 **프로젝트 간 격리**를 보안 규칙 테스트(에뮬레이터)로 검증
- 사이클 삭제는 유예 없이 사이클의 Firestore 문서와 Storage 증거를 바로 지운다(F-CY-10).
- 프로젝트 삭제 시 유예 기간 후 관련 데이터·비밀값·Storage 파일을 영구 삭제(F-TM-12). 지운 Storage 파일은 버킷 소프트 삭제 정책으로 최대 7일 더 복구 가능한 상태로 남는다. 실행자 PC의 빌드 캐시·업로드 큐와 Anthropic으로 보낸 데이터는 qcard가 지우지 못하므로 개인정보처리방침에 적는다. 탈퇴한 멤버는 즉시 접근 불가
- **로컬 콘솔 보호**: `127.0.0.1`에만 바인딩. 호스트 에이전트가 일회용 토큰 URL로 브라우저를 열고 세션 쿠키(HttpOnly, SameSite=Strict)로 교환. 웹에서 여는 경우(F-DB-10) 일회용 주소(2분·1회)는 본인만 읽을 수 있는 호스트 문서로만 전달. 모든 HTTP·WebSocket 요청에서 Host·Origin 헤더를 검사해 다른 웹페이지의 요청과 DNS 리바인딩을 차단

## 12. 용어
- **QA 문서**: 앱 버전마다 스펙 묶음에서 생성하는 케이스 묶음. 기준은 Firestore 케이스 문서이며, MD는 읽기 전용으로 렌더링한 산출물이다.
- **테스트 사이클**: QA 문서 버전 + 빌드 + 대상 디바이스로 정의하는 테스트 단위. 여러 Run을 묶어 하나의 결과(웹 QA 시트)를 만든다.
- **Run**: 한 실행자가 한 디바이스로 사이클의 케이스를 수행하는 1회 실행.
- **QA 시트**: 사이클의 케이스 목록과 디바이스별 결과를 담은 표. MVP에서는 웹으로만 제공한다(§5.10).
- **준비 플로우**: "로그인 상태" 같은 공통 사전조건을 확인 조건 + 수행 스텝으로 정의한 재사용 단위. QA 문서 버전마다 사본을 두고, 새 버전은 이전 버전에서 이어받는다.
- **검증 포인트**: 기대결과를 확인 가능한 단위로 나눈 것. 포인트마다 관찰값·증거를 기록한다.
- **스텝 타임라인**: 스텝별 액션·의도·액션 표시 스크린샷·영상 시점(P1)의 기록.
- **시작 전**: 판정된 칸도 실행 중인 Run도 없는 사이클의 표시. 저장하는 상태가 아니라 결과·Run으로 계산하며, 목록에서는 "시작 전" 칩에 따로 모은다(F-CY-09). Run 요청이 호스트를 기다리는 "호스트 대기"·Run의 "승인 대기"와 구분한다.
- **사이클 완료**: QA 권한자가 사이클을 끝났다고 표시한 상태. 새 Run을 받지 않는다(F-CY-09).
- **케이스 수정안**: 스펙 확인 질문의 답변을 반영해 QA Doc Generator가 만든 케이스 변경 제안. 사람이 diff를 보고 적용해야 케이스가 바뀐다(F-QD-17).
- **확인필요**: Agent가 판정하지 못했거나 자동 확정 조건을 충족하지 못한 상태 — 사람 확정 대상.
- **호스트 에이전트(Host Agent)**: 디바이스가 연결된 실행자 PC에서 동작하며 디바이스 제어·로컬 콘솔·Agent 실행 루프·결과 업로드를 담당하는 프로그램.
- **호스트 연결**: 웹에 로그인한 사용자가 [이 PC 연결]로 호스트 에이전트를 자기 계정에 묶는 것. 호스트는 이때 받은 호스트 자격으로 접속하며 따로 로그인하지 않는다.
- **로컬 콘솔**: 호스트 에이전트가 `localhost`로 띄우는 실행 화면. 라이브 화면·액션 오버레이, 스텝 타임라인, Agent 사고 로그, 제어 버튼 제공.
- **Take over**: 실행 중 사용자가 디바이스 조작 권한을 가져오는 것.
- **위험 액션**: 실행하면 테스트 밖에 영향을 주거나 되돌릴 수 없는 액션. **승인 필요**(실행자가 승인하면 Agent가 실행)와 **사람 전용**(본인인증처럼 Agent가 하면 안 되고 실행자가 직접 수행) 두 등급이 있다(F-EX-10).
- **프로젝트(QA 대시보드)**: 앱 하나에 대한 QA 작업 공간. 멤버·권한·데이터의 단위이며, 사용자가 만들고 초대·탈퇴·삭제한다.
- **Claude Code 연결**: 호스트 에이전트가 같은 PC에 설치된 사용자 본인 로그인의 Claude Code를 헤드리스로 실행해 LLM을 호출하는 방식(§8 옵션 D).
- **환산 비용**: 사용한 토큰을 Anthropic API 단가로 계산한 참고값. 실제 청구액이 아니며, 실제로는 사용자의 플랜 사용량에서 차감된다.
