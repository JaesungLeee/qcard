# 준비 플로우와 테스트 계정

케이스의 사전조건을 Agent가 UI로 만드는 방법과, 로그인이 있는 앱에서 테스트 계정을 나눠 쓰는 방법이다.

코드: 규칙 `packages/shared/src/prepFlows.ts`·`accounts.ts`, 배정·암호화 `apps/functions`, 호스트 쪽 `apps/host-agent/src/accounts.ts`, 화면 `apps/web/src/features/qa-doc/PrepFlowPage.tsx`·`features/accounts`.

## 준비 플로우

"로그인 상태", "항목 2개 보유" 같은 공통 사전조건을 **확인 조건 + 수행 스텝**으로 정의하고, 케이스가 이를 참조한다. 종류는 로그인(`login`)·데이터 상태(`data_state`)·환경(`env`)·원복(`restore`)이다.

- QA 문서를 만들 때 스펙의 Given에서 플로우 후보를 뽑아 제안한다.
- Admin·QA가 웹에서 버전을 골라 추가·편집·삭제하고, Viewer는 읽기만 한다. 로그인이 있는 앱은 **로그인 플로우를 팀이 직접 맞춰야** 계정 풀이 동작한다.
- 편집이 겹치면 케이스 편집처럼 `rev`로 충돌을 알리고 최신 내용을 보인다.
- 플로우 내용은 케이스 승인 해시에 들어가지 않는다. 로그인 플로우를 고쳐도 문서 전체가 미승인으로 돌아가지 않는다.
- **로그아웃 플로우는 두지 않는다.** 계정이 바뀌면 앱 데이터를 초기화하므로, "로그아웃 상태"는 환경 플로우로 나타낸다.

### 버전과 이어받기

- 준비 플로우는 **QA 문서 버전마다 사본**을 둔다. 같은 ID·같은 내용이어도 따로 저장한다. 새 버전에서 고친 플로우가 이전 버전 사이클(예: 1.0.1 다음에 1.0.0을 다시 돌리는 경우)에 영향을 주지 않게 하려는 것이다.
- **새 버전은 이전 버전에서 이어받는다.** 이전 버전의 플로우 전체를 기존 목록으로 생성에 넘기고, 새 버전에는 케이스가 참조하는 것만 같은 ID·같은 내용(사람이 고친 것 포함)으로 복사한다. 기존 목록에 없는 플로우만 새로 만든다. 쓰이지 않게 된 플로우는 이전 버전에만 남는다.
- 생성은 이전 버전에 있는 ID의 내용을 바꾸지 않는다. 스펙 Given이 바뀌어 다른 준비가 필요하면 새 ID로 만든다.
- **편집은 그 버전에만 적용된다.** 준비 플로우는 사이클에 복사하지 않으므로, 그 버전으로 만든 진행 중인 사이클에는 다음 Run부터 적용된다.
- 그 버전의 활성 케이스나, 그 버전으로 만든 완료되지 않은 사이클의 케이스 사본이 참조하는 플로우는 지울 수 없다. 화면에 그 플로우를 쓰는 케이스를 보인다(Functions가 트랜잭션에서 확인).

### 실행

- 실행할 때 준비 플로우를 UI로 수행한다. **준비에 실패하면 그 케이스는 Blocked**다(로그인 실패 포함).
- 이미 충족된 상태여도 매번 준비한다. 상태를 먼저 확인해 건너뛰는 것은 속도 최적화라 아직 없다.

## 케이스 사이의 앱 상태

- 기본은 **앱 강제 종료 후 재시작**이다(데이터 유지).
- 케이스에 "클린 상태 필요"가 있으면 앱 데이터를 초기화한다(`pm clear`). 로그인이 없는 앱(익명 인증 등)은 초기화 = 새 사용자이므로, "빈 사용자" 상태를 만드는 기본 수단이다.
- **데이터 상태**(항목 0개 / 1개 / 2개 이상, 저장된 기록 있음)는 앱 데이터를 초기화한 뒤 준비 플로우를 UI로 수행해 만든다.
- 계정 종류·준비 상태가 같은 케이스끼리 묶어 연달아 실행하고, 묶음 안에서는 정의된 순서대로 실행한다.

## 테스트 계정 풀

로그인이 있는 앱에서 여러 실행자가 계정을 나눠 쓰는 방법이다.

### 적용 조건

프로젝트 설정 플래그 없이 **케이스의 필요 계정 종류로만** 정한다. 설정과 케이스가 어긋나지 않게 사실을 한 곳에 둔다.

- 종류가 있는 케이스만 계정을 배정받고, 없는 케이스는 배정 없이 진행한다.
- QA 문서에 종류가 있는 케이스가 하나도 없으면(로그인이 없는 앱) 배정 호출·계정 경고가 없고, 테스트 계정 화면은 "계정이 필요한 케이스가 없음"을 보인다.
- 같은 종류의 계정은 서로 바꿔 쓸 수 있다고 본다. 여러 실행자가 동시에 돌리거나 한 계정이 격리돼도 같은 종류의 다른 계정으로 진행한다.
- 한 계정은 종류 하나다. 성질이 겹치면 "구독자 관리자"처럼 별도 종류를 만든다.

### 등록

- 웹 사이드바의 **테스트 계정** 화면에서 Admin·QA가 로그인 ID·비밀번호·TOTP 시드(선택, `otpauth://` URI 또는 base32)·메모·계정 종류를 등록·수정·삭제한다.
- 비밀값은 Functions가 암호화해 저장하고 **다시 보여 주지 않는다.** "설정됨·마지막 변경 시각·변경한 사람"만 보이고, 바꿀 때는 덮어쓴다([security.md](../security.md#테스트-계정-비밀값)).
- **계정 종류는 필요할 때만 드러낸다.** QA 문서에 쓰인 종류가 "기본" 하나뿐이면 등록 폼에 종류 칸이 없다. 다른 종류가 쓰이면 종류 선택과 종류별 계정 수·케이스 수가 나타나고, 계정이 0개인 종류를 경고한다.
- Run을 시작하기 전에 로컬 콘솔이 고른 케이스에 필요한 종류 중 계정이 없는 종류를 알린다.
- 리스 중인 계정은 지울 수 없다.

### 배정과 반납

- **케이스 단위로 배정한다.** 케이스를 시작할 때 호스트가 필요한 종류의 빈 계정 하나를 Functions 트랜잭션으로 잠그고(리스), 그 응답으로 비밀값을 받는다. 후보는 격리·로그인 실패 표시가 없는 계정뿐이다.
- 이전 케이스와 종류가 같으면 그대로 쓴다. 다르면 이전 계정을 반납하고 앱 데이터를 초기화한 뒤 로그인 플로우로 다시 로그인한다.
- 디바이스에 다른 계정의 로그인이 남지 않도록, 계정이 바뀌거나 계정이 필요 없는 케이스로 넘어가면 클린 상태가 아니어도 앱 데이터를 초기화한다.
- 이어 쓰던 계정의 배정이 풀렸으면 새 계정을 받는다.
- **반납**: 종류 전환, Run 종료, 리스 만료(Run 연결 신호가 끊김 — 칸 선점과 같은 신호).
- 후보가 없으면 그 케이스는 Blocked("계정 없음")이고 다음 케이스로 간다.
- 계정은 사이클에 고정하지 않는다.

### 로그인 실패

- 로그인 플로우에서 **앱이 계정 정보를 거절하면**(비밀번호 오류·계정 잠김 메시지) 그 케이스는 Blocked("로그인 실패")다. 계정은 반납하되 "로그인 실패" 표시를 붙여 배정에서 뺀다(앱의 계정 잠금을 막으려고). 비밀번호를 고치거나 [표시 해제]하면 다시 배정된다.
- 요소를 못 찾는 등 계정 탓이 아닌 실패는 표시하지 않는다.
- 한 Run에서 같은 종류의 로그인이 2번 실패하면 플로우 탓으로 보고 그 종류의 계정을 더 받지 않는다(남은 케이스 Blocked "로그인 플로우 확인 필요"). 잘못된 플로우가 풀의 계정을 차례로 막지 않게 하려는 것이다.

### 원복과 격리

- 계정 상태를 바꾸는 케이스(프리미엄 전환, 설정 변경 등)는 **원복 플로우**를 참조한다. QA 문서를 만들 때 이런 케이스를 찾아 원복 플로우 후보를 제안한다.
- 케이스가 끝나면 판정과 상관없이 원복을 수행한다. 원복 결과는 그 케이스 판정에 영향을 주지 않는다.
- **원복에 실패하거나, 원복 플로우가 있는 케이스 도중 리스가 만료되면** 계정을 반납하지 않고 **격리**한다. 웹 계정 목록에 사유·케이스·시각을 보이고, Admin·QA가 직접 원복한 뒤 [격리 해제]한다.
- 되돌릴 수 없는 계정 변경(탈퇴·삭제)은 원복할 수 없으므로 Manual이다.
