# 스펙 수집과 QA 문서

앱 버전마다 스펙 묶음 전체에서 **QA 문서 1개**를 만든다. QA 문서의 기준은 Firestore의 케이스 문서이고, 편집은 웹에서만 한다. 생성은 웹에서 요청하고 **요청자의 호스트**가 요청자 본인의 Claude 플랜으로 한다. 호스트가 꺼져 있으면 웹이 켜는 방법을 안내한다.

코드: 파서·매칭 `packages/spec`, 생성 `packages/qadoc`, 화면 `apps/web/src/features/qa-doc`. 명령은 [dev/spec-qadoc.md](../dev/spec-qadoc.md), 스펙 형식은 [spec-format.md](../spec-format.md).

## 스펙 업로드

- 앱 버전마다 스펙 폴더 전체를 **폴더나 ZIP으로** 올린다. 상대 경로를 지키고 `<스펙 이름>/spec.md`만 입력으로 쓴다(폴더 이름 = 스펙 이름, 예: `room-list`). 같은 폴더의 plan·tasks·research 등은 무시한다.
- 올린 스펙은 **바꿀 수 없는 스냅샷**이다. 원본 근거 링크가 늘 맞게 하려고 덮어쓰기를 막는다.
- 일부 기능만 올리는 부분 업로드는 없다. 스냅샷에서 빠진 스펙의 케이스는 "삭제"가 된다.
- 지금은 Storage에 `spec.md`만 저장한다.

## 생성

- QA 문서는 스펙(기능) 단위 섹션, 유저 플로우 단위 하위 섹션으로 나뉜다.
- **케이스는 스펙의 테스트 시나리오(TS)·엣지 케이스(EC) 표의 행에서만 만든다.** 각 행을 사전조건·단계·검증 포인트·수행 방식을 갖춘 실행 가능한 케이스로 바꾼다. 측정 가능한 성과(SC)는 케이스가 아니다.
- 요구사항은 스펙의 FR·UX를 그대로 쓰고 `<스펙 이름>/FR-xxx`로 구분한다. 요구사항·케이스마다 원본 근거(스펙 파일·헤딩 경로·줄)를 둔다.
- 플랫폼 필드(공통 / Android / iOS)는 두지만, 지금은 **공통·Android 케이스만** 만든다.
- 결정적인 부분(매칭·복사·ID·해시·승인 상태)은 코드가, 신규·변경 행의 케이스 변환·준비 플로우·확인 질문·보강 제안은 Opus가 한다(`packages/qadoc/src/prompts.ts`).

### 케이스 필드

제목, 요구사항 ID, 사전조건(준비 플로우 참조), 클린 상태 필요 여부, **필요 계정 종류**, 원복 플로우, 테스트 데이터, 단계, 검증 포인트, 우선순위, 유형, 플랫폼, 수행 방식.

**필요 계정 종류**는 이 케이스가 테스트 계정을 배정받는다는 뜻이다.

- 로그인이 필요한 케이스의 기본값은 "기본"이다.
- 구독 등급·권한·계정 유형처럼 **실행 중 UI로 만들 수 없는 계정 성질**이 Given에 있을 때만 다른 종류("구독자", "관리자")를 붙인다. 항목 수·설정값처럼 UI로 만들 수 있는 상태는 종류가 아니라 준비 플로우다.
- 로그인 상태로 시작할지는 준비 플로우가 정한다. 로그인 화면 자체를 테스트하는 케이스도 계정 정보를 쓰면 종류를 지정하고 "로그아웃 상태" 플로우로 시작한다.
- QA 문서 화면에서 여러 케이스에 한꺼번에 지정할 수 있다.

**검증 포인트**는 생성할 때 정의하고 함께 승인한다: 대상 설명, 비교 종류(텍스트 존재·표시·미표시·개수·크기(dp)·상태·화면), 기대값, 확인 방법(접근성 트리·비전).

### 수행 방식과 위험 표시

- 케이스 단위로 Auto / Manual, Auto 케이스 안에서는 **스텝 단위 "수동"** 표시(예: SMS OTP 입력).
- 다음은 Manual이다: 다중 사용자 케이스(방장/멤버, 초대 수락 등 다른 사용자의 행동이 필요한 경우), 서버 이벤트가 필요한 케이스(푸시 수신 등), 화면으로 확인할 수 없는 케이스(요청 헤더·서버 검증 등), 되돌릴 수 없는 계정 변경(탈퇴·삭제).
- 단계마다 **위험 표시**(승인 필요 / 사람 전용)를 붙이고 검토 화면에 보인다. 본인인증·인증번호·소셜 로그인 단계는 사람 전용이라 수동 스텝으로 만든다. 등급의 뜻은 [execution.md](execution.md#위험-액션)에 있다.

## 버전 매칭과 ID 이어받기

버전마다 새로 만들되, 이전 버전 QA 문서와 **출처 ID(`<스펙 이름>/TS-xxx`·`EC-xxx`)로 결정적으로 매칭한다.** LLM은 매칭하지 않는다.

| 판정     | 조건                                 | 처리                                                                                                                                                     |
| -------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **동일** | 출처 행과 관련 FR의 내용 해시가 같다 | LLM을 거치지 않고 이전 케이스를 그대로 복사한다. 사람의 수정·승인이 남는다                                                                               |
| **변경** | 해시가 다르다                        | 같은 TC ID로 다시 만든다. 사람이 고친 이전 케이스와 스펙 diff를 함께 넘겨 아직 유효한 수정은 지킨다. 검토 화면에 이전 대비 diff를 보이고 다시 승인받는다 |
| **신규** | 이전에 없던 출처                     | 새 TC ID                                                                                                                                                 |
| **삭제** | 스냅샷에서 사라진 출처               | 삭제로 표시                                                                                                                                              |

이 매칭은 **스펙 작성자가 TS·EC ID를 지운 뒤 다시 쓰지 않는다**는 전제에 기댄다([spec-format.md](../spec-format.md#id-규칙)).

준비 플로우도 이어받는다. 규칙은 [prep-flows.md](prep-flows.md#버전과-이어받기)에 있다.

## 스펙 확인 질문

- 모호하거나 빠진 스펙을 확인 질문으로 따로 보이고, 코멘트를 단다.
- **답이 없는 질문에 연결된 케이스는 승인이 보류된다.** 나머지 케이스는 그대로 진행한다. QA 권한자가 "현 스펙대로 진행"을 고르면 보류가 풀린다.
- 질문은 연결된 케이스의 기능 › 유저 플로우 카테고리별로 모아 한 카테고리씩 처리한다.
- 스펙만으로 로그인 필요 여부가 분명하지 않으면 "로그인이 필요한 앱인가요?" 질문을 만든다.

## 스펙 보강 제안

테스트 설계 기법(정상 플로우, 예외·부정, 경계값, 동등분할, 상태 전이, 권한·역할별)으로 FR·UX 규칙 대비 빠진 TS·EC를 찾아 FR별로 제안한다(예: "room-list FR-011 카테고리 칩 선택 TS 없음"). 제안은 케이스가 아니다. 스펙 작성자가 TS·EC를 보태면 다음 버전부터 케이스가 된다.

## 편집과 승인

- 상세 폼에서 케이스 단위로 편집한다(그리드는 읽기 전용). 케이스마다 `rev`를 두고, 저장할 때 다른 사람이 먼저 저장했으면 거부하고 최신 내용과 내 편집을 비교해 다시 저장하게 한다(낙관적 잠금).
- 승인은 **TC ID + 내용 해시**에 붙는다. 승인된 케이스만 사이클에 들어간다. 내용이 바뀌면 저절로 미승인이 된다. 일괄 승인·반려가 있다.
- 요구사항 ↔ 케이스 **추적성 매트릭스**와 커버리지를 보이고, 케이스가 없는 요구사항을 경고한다.

## 답변 기반 케이스 수정안

답변된 확인 질문에서 QA 권한자가 [케이스 수정안 만들기]를 누르면 **요청자 본인의 호스트**가 연결 케이스마다 수정안을 만든다.

- 답변자(기획자·개발자)는 호스트가 없을 수 있으므로 **답변할 때 자동으로 요청하지 않는다.**
- 입력은 현재 케이스, 출처 스펙 행, 그 케이스의 처리된 질문이다. 출력은 **수정안**(바꾼 케이스 + 근거) 또는 **수정 불필요**(이유)다.
- 웹에서 현재 케이스 대비 diff로 보고 적용하거나 버린다. 적용은 일반 편집과 같은 낙관적 잠금이고, 적용하면 미승인이 된다. 적용·버리기는 요청한 사람만 한다.
- 요청 뒤 케이스가 바뀌었으면 그 수정안은 버리고 지금 케이스로 다시 만든다.
- 호스트는 진행 중인 작업을 끊지 않되, 다음 작업을 고를 때 수정안을 QA 문서 생성보다 먼저 처리한다.
- "현 스펙대로 진행"으로 처리한 질문은 바꿀 내용이 없으므로 대상이 아니다.
