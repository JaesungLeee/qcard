# 결과와 QA 시트

사이클의 결과를 보고, 확정하고, 공유하는 규칙이다. **QA 시트는 웹이 유일한 형태다.**

코드: 집계 `packages/data/src/logic.ts`, 판정 `packages/shared/src/verdict.ts`, 화면 `apps/web/src/features/qa-sheet`.

## QA 시트 구성

사이클 단위 화면이다. 탭마다 고유 주소(`?tab=`)가 있다.

| 탭            | 내용                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 요약          | 프로젝트명, QA 문서 버전, 대상 빌드(앱 버전·빌드 번호), 테스트 기간, 대상 디바이스, 판정별 건수·통과율(전체/디바이스별), 주요 결함 |
| 테스트 케이스 | 케이스와 디바이스별 결과(아래 컬럼). 결과 칸을 열면 판정 추적                                                                      |
| 결함          | 결함 ID, 제목, 심각도, 관련 TC ID, 디바이스/OS, 재현 절차, 기대/실제 결과, 상태, GitHub 이슈                                       |

실제 결과는 컬럼으로 두지 않는다. **Fail·확인필요 칸에서만 한 줄 요약**을 보이고, 전체는 판정 추적에서 본다.

판정 칸 색: Pass 초록, Fail 빨강, Blocked 주황, N/A·N/T 회색, 확인필요 노랑. 판정 값의 뜻은 [concepts.md](../concepts.md#판정).

## 판정 추적

케이스 × 디바이스 결과에서 **행동 의도 → 스텝 타임라인(액션 표시 스크린샷) → 검증 포인트(기대·관찰값·증거) → 판정 이유**까지 따라간다.

## 자동 확정

다음을 모두 채우면 Agent Pass를 자동 확정하고, 하나라도 못 채우면 확인필요로 둔다. 채운·못 채운 조건 목록을 결과에 남긴다.

1. 모든 검증 포인트가 일치 (`all_match`)
2. 모든 검증 포인트를 접근성 트리로 확인 — 비전으로만 확인한 포인트가 있으면 안 됨 (`tree_only`)
3. Take over·스텝 건너뛰기 없음 (`no_takeover`)
4. 자가 복구 횟수가 한도 안 (`within_retry`)

2번은 완화하지 않는다. 비전 판정이 사람 판정과 얼마나 맞는지 데이터가 쌓이면 다시 본다([roadmap.md](../roadmap.md)).

## 사람 확정

- Fail·Blocked·확인필요는 사람이 확정한다. 자동 확정된 Pass도 사람이 뒤집을 수 있고, 뒤집힌 자동 Pass는 결과에 표시한다.
- 보안 규칙이 **판정자 = 로그인 사용자**와 서버 시각을 강제하고, 판정 변경 이력은 바꿀 수 없는 로그로 남긴다.

## 수동 케이스 결과

- 웹 그리드에서 판정·실제 결과·스크린샷 첨부를 입력한다.
- **스크린샷은 선택이다.** 화면으로 확인할 수 없는 케이스, 다른 사람 폰에서 결과가 나는 케이스가 있고, 본인인증 화면처럼 올리면 안 되는 화면이 있어서다. Fail·Blocked에서 첨부가 없으면 권유 문구만 보이고 저장은 막지 않는다.
- 5장, PNG/JPEG/WebP, 한 장 10MB까지. 붙여넣기도 된다. 판정을 확정할 때만 바뀌고 이력에 장수가 남는다. Storage `cycles/{c}/manual/` 아래라 사이클·프로젝트 삭제 때 함께 지워진다.

## 결함

- Fail 결과(판정 추적, 확정 패널)에서 결함을 만든다. TC ID·디바이스/OS·빌드·재현 절차·기대/실제 결과·증거(결과 주소)를 미리 채운다.
- 번호 `D-n`은 사이클 안에서 이어진다(보안 규칙이 번호를 확인).
- 심각도(critical·major·minor·trivial)와 상태(open·fixed·closed)를 결함 탭에서 바꾼다.
- 결함이 없는 Fail 칸을 사이클 카드·요약·케이스 그리드에 표시한다.
- 결함마다 연결한 GitHub 저장소에 이슈로 발행할 수 있다. 이슈가 연결된 결함의 상태는 이슈와 양방향으로 맞춘다([issues.md](issues.md)).
- fixed 결함은 더 새 빌드의 사이클에서 다시 확인해 closed 또는 open으로 확정한다([재테스트](#재테스트)).

## 재테스트

이전 사이클의 fixed 결함을 더 새 빌드로 만든 사이클에서 다시 돌려 보고, 그 결과로 결함을 닫거나 다시 연다. 재테스트만 하는 사이클 종류는 따로 두지 않는다. 새 빌드 사이클이 회귀와 재테스트를 함께 한다. 이슈가 없는 결함도 같은 방식으로 재테스트한다.

코드: 규칙 `packages/shared/src/retest.ts`, 목록 `packages/data/src/logic.ts`(`retestList`), 확정 Functions `confirmRetest`(`apps/functions/src/issues.ts`), 화면 `apps/web/src/features/qa-sheet/RetestSection.tsx`.

### 대상

사이클 B의 재테스트 대상은 같은 프로젝트의 **다른 사이클 결함 중 아래 조건을 모두 채우는 것**이다.

- 상태가 fixed다.
- B의 빌드가 결함 사이클의 빌드보다 새 빌드다. 패키지명이 같고 빌드 번호(versionCode)가 더 커야 한다. 그 빌드에 수정이 실제로 들어갔는지는 qcard가 알지 못한다.

B에서 이미 확정한 결함은 그 뒤 상태가 바뀌어도 B의 목록에 남아 확정 결과를 보인다. 다시 fixed가 돼도 B에서는 다시 확정하지 않는다 — B의 칸 결과는 고치기 전 빌드의 것이다. 확정한 결함의 칸은 "재테스트 대상" 필터와 "재테스트 D-n" 표시에서 빠진다. 로컬 실행 묶음·삭제 중인 사이클은 재테스트를 받지 않는다(Functions도 거부한다).

대상 결함마다 B 안에서 **재테스트 칸**을 찾는다. B의 케이스 스냅샷에서 같은 TC ID를 찾고, 결함이 난 디바이스와 모델·OS 메이저가 같은 B의 대상 디바이스를 찾는다. 이 둘이 만나는 칸이 재테스트 칸이다.

| 경우                                           | 표시                                  | 확정                                       |
| ---------------------------------------------- | ------------------------------------- | ------------------------------------------ |
| 칸을 찾음                                      | 재테스트 칸과 그 판정                 | 아래 [결과 읽기](#결과-읽기)대로           |
| 칸을 찾았지만 케이스 내용 해시가 다름          | 위와 같고 "케이스 바뀜"을 함께 보인다 | 막지 않는다                                |
| B의 스냅샷에 그 TC ID가 없음                   | "케이스 없음"                         | 할 수 없다. 결함 상태를 사람이 직접 바꾼다 |
| B에 같은 모델·OS 메이저의 대상 디바이스가 없음 | "대상 디바이스 없음"                  | 위와 같다                                  |

수동 케이스도 칸 결과가 있으면 같은 방식으로 재테스트한다.

### 결과 읽기

재테스트 칸의 **최종 판정**(재실행했으면 최신 결과)을 본다.

| 칸 판정                            | 표시           | 제안                          |
| ---------------------------------- | -------------- | ----------------------------- |
| Pass (자동 확정 또는 사람 확정)    | 재테스트 Pass  | [closed로 확정]               |
| Fail (사람 확정)                   | 재테스트 Fail  | [다시 열기]                   |
| 사람 확정 전 Fail                  | Fail 확정 필요 | 칸을 먼저 확정하라고 안내한다 |
| 확인필요·Blocked·N/A·N/T·결과 없음 | 그 판정 / 남음 | 없음                          |

- **상태는 사람이 확정한다(QA·Admin).** qcard가 결과만 보고 결함 상태를 바꾸지 않는다. 재테스트 Pass인 결함 여러 건을 한 번에 closed로 확정할 수는 있다.
- B가 완료된 뒤에도 확정할 수 있다. 사람 확정이 완료 뒤에도 열려 있는 것과 같다.

### 확정하면

- **closed로 확정**하면 결함을 closed로 바꾸고 재테스트 기록을 남긴다. 기록에는 사이클 B, 빌드(버전·빌드 번호), 칸 판정, 판정 추적 주소, 확정한 사람, 시각이 들어간다.
- **다시 열기**를 하면 결함을 open으로 바꾸고 같은 재테스트 기록을 남긴다. B의 Fail 칸은 이 결함(사이클 이름 + `D-n`)을 가리키게 되고(결과 칸 `defectCycleId`), "결함이 없는 Fail"로 세지 않는다. 증상이 다르면 다시 열지 말고 B에 새 결함을 만든다. B의 칸에 이미 다른 결함이 연결돼 있으면 다시 열기를 막는다 — 같은 증상이면 결함 사이클에서 상태를 직접 바꾼다.
- 다시 연 결함이 나중에 또 fixed가 되면, 그다음 새 빌드 사이클에서 다시 재테스트 대상이 된다(B에서는 확정한 결과만 보인다). 재테스트 기록은 결함에 쌓이고 최근 것이 위에 온다.
- 이슈가 연결돼 있으면 이슈 상태와 코멘트에 반영한다([issues.md](issues.md#상태-동기화)).
- 확정은 **Functions가 한다.** Functions가 서버에서 재테스트 칸 결과를 다시 읽어 판정을 확인한 뒤, 결함·칸·이슈를 바꾼다. 확인할 때 결함 상태가 fixed가 아니면 거부한다. GitHub 호출이 실패했을 때의 처리는 기존 상태 변경 규칙과 같다. GitHub를 부르는 동안 다른 요청이 같은 결함을 이 사이클에서 먼저 확정했으면 기록을 겹쳐 남기지 않고, 칸에 다른 결함이 연결됐으면 칸을 덮어쓰지 않는다. 상태는 다른 상태 변경과 같이 나중에 쓴 쪽을 따른다.

| --------------------- | --------------------------------------------------------------------------------------------------------------- |

### 삭제

- **결함 사이클을 지우면** 결함도 함께 지워지므로 B의 대상 목록에서 빠진다. B 칸에 남은 결함 연결은 "삭제된 결함"으로 보인다.
- **B를 지우면** 결함의 재테스트 기록은 남는다(빌드·판정·시각). 다만 기록 속 판정 추적 주소는 열리지 않는다. 결함 상태는 바뀌지 않는다.

## 공유

웹 화면 주소가 곧 공유 링크다. QA 시트(탭 포함)·판정 추적 결과마다 고유 주소가 있고, 로그인하지 않았으면 로그인 후 그 주소로 돌아오며, 멤버가 아니면 보안 규칙이 막는다. [링크 복사] 버튼, 별도 리포트 화면, 멤버 밖 공개 링크는 두지 않는다.
