## 다음 할 일

### M1 완료 — 운영 환경에서 2인 사이클

**완료 기준**: 실제 스펙 1건으로 팀원 2명 이상이 서로 다른 디바이스로 한 사이클을 끝까지 수행하고 결과를 공유한다. **운영 환경**(qcard.dev, 배포된 Functions·KMS, npm으로 설치한 호스트)에서.

테스터를 확보한 뒤 진행한다(2026-10-27 결정). 흐름: 스펙 업로드 → QA 문서 생성 → 승인 → 빌드 업로드·사이클 생성 → 두 사람이 각자 `qcard serve`로 서로 다른 디바이스에서 실행 → 웹에서 확정. 테스트 계정 풀은 배포된 Functions·KMS로 확인한다. 실기기·배포된 Functions로 계정 풀을 끝까지 돌린 기록은 아직 없다.

시작 전에 첫 사용 팀과 합의할 것:

- 스펙 작성 규칙 — TS·EC ID를 지운 뒤 다시 쓰지 않기([spec-format.md](spec-format.md#id-규칙)). 버전 매칭의 전제다.
- 테스트 식별자 — `testTagsAsResourceId` 켜기와 주요 요소 testTag 추가.

## 알려진 빈틈

| 영역          | 빠진 것                                                                                                                                      |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 스펙 업로드   | `spec.md`만 받고 TXT는 받지 않는다. 코드블록·일반 목록·링크 이미지 구조는 다루지 않는다. Storage에 `spec.md`만 저장한다                      |
| 원본 근거     | 줄 범위가 늘 한 줄이고, 원문 링크가 없다                                                                                                     |
| 디바이스 목록 | 배터리는 목업이다. 디바이스 1대만 보인다                                                                                                     |
| 검증 포인트   | 트리에 노드가 없는 요소는 셀 수 없어 확인필요로 남는다(앱 쪽 testTag가 해법)                                                                 |
| 초대          | 사용자명 초대도 받는 사람에게 알림이 없다                                                                                                    |
| 액션 오버레이 | 실행 후 1.5초 보인다. 실행 전 미리 보기는 없다                                                                                               |
| 이슈 동기화   | 놓친 웹훅을 다시 받지 않는다. 조직 `.github` 저장소의 공용 이슈 템플릿을 읽지 않는다                                                         |
| 이슈 발행     | 이슈를 만든 뒤 결함 기록이 3번 모두 실패하면, 발행 중 표시가 2분 뒤 풀려 다시 발행할 수 있다(해법: 본문 표식으로 이미 만든 이슈를 찾아 연결) |
